# Problemas conocidos

| ID | Estado | Descripción | Mitigación actual |
| --- | --- | --- | --- |
| F0-001 | Cerrado | WSL2, Podman, QEMU y OVMF están disponibles dentro de Ubuntu. La base bootc y el CLI unificado `image-builder` `linux/amd64` se descargaron por digest en un store dedicado; se registraron versión, commit, mounts, rutas permitidas y un gate limitado al experimento manual. | Evidencia: `packaging/phase0-image-manifest.template.yaml`, `docs/testing/registry-inspection-2026-07-19.md` y la inspección aislada de `bootc`. Cada invocación que cambie estado sigue requiriendo aprobación explícita. |
| F0-002 | Cerrado | Se construyó una OCI derivada por digest y se generó el artefacto `images/phase0-f44-20260718/aureon-base.qcow2`. | Evidencia: `build/phase0-f44-20260718/derived-oci.json` y `build/phase0-f44-20260718/qcow2.json`. `aureon-dev build/image` siguen siendo planes seguros, no runners. |
| F0-003 | Cerrado | `/dev/kvm` estuvo disponible y la VM documentada usó KVM; el log serial registra el cierre de virtualización por hardware. | Evidencia: `work/qemu/phase0-f44-20260718/smoke.json`. No usar una única duración como benchmark ni inferir disponibilidad permanente de KVM. |
| F0-004 | Cerrado | Se auditó `podman-auto-update.timer`, `podman.socket` y `qemu-kvm.service`; estaban habilitados por el paquete y se detuvieron/deshabilitaron dentro de Ubuntu WSL. | Evidencia: `systemctl list-unit-files` informa los tres como `disabled`. No hubo cambios a servicios de Windows. |
| F0-005 | En validación | `doctor` ya consulta de solo lectura la distro fija `Ubuntu-24.04` desde Windows y comprueba arquitectura, Python, Podman, QEMU, `qemu-img`, OVMF y KVM opcional dentro del guest. | Las pruebas unitarias cubren los probes y rutas confiables de `wsl.exe`; falta validar la salida real desde la sesión Windows propietaria de WSL antes de cerrarlo. |
| F0-006 | Abierto | El conversor histórico `bootc-image-builder` fijado por digest informó `build_tainted: true` al ejecutar `--version` sin red ni privilegios. Está excluido del experimento; se seleccionó el CLI unificado `image-builder`, que inspeccionó la base correctamente. | No usar el conversor histórico para Fase 0. Mantener la observación abierta para una decisión de release o hasta contar con explicación upstream verificable. |
| F0-007 | Cerrado | El primer intento de conversión se detuvo durante la generación de manifiesto: el lector `containers-storage` esperaba su ruta canónica, mientras el Podman interno necesitaba conservar la ruta estática del store dedicado. No se creó ningún `qcow2` en ese intento; el mapeo corregido produjo el `qcow2` final sin red. | Evidencia: `build/phase0-f44-20260718/conversion-attempt-01.json` y `build/phase0-f44-20260718/qcow2.json`. El segundo mount interno apunta al mismo store dedicado, sin usar store global. |
| F0-008 | Abierto | El log de apagado del guest contiene AVC de SELinux de `mdadm` contra una ruta overlay después de iniciar `systemd-shutdown`. El guest llegó a `poweroff.target`, QEMU salió con `0` y el overlay pasó `qemu-img check`. | Conservar el log y revisar la causa antes de un perfil release; no ocultar la observación ni tratarla como fallo del smoke funcional. |
| F0-009 | En validación | La cadena OCI → `qcow2` → QEMU se ejecutó manualmente para un único build ID. `aureon-dev test-smoke --execute` ya implementa una cadena acotada con rutas nuevas, imágenes locales por digest, red apagada, store dedicado, overlay, logs y evidencia; `build --execute` e `image --execute` permanecen cerrados. | Ejecutar el runner desde el WSL propietario con un build ID nuevo, conservar la evidencia y repetir desde un checkout limpio antes de cerrarlo. |

| D1-001 | En validación | `preview-08` y `preview-09` se construyeron antes de incorporar `aureonctl` al overlay. Pueden abrirse con `--run-existing`, pero los comandos nuevos estarán dentro del guest solo tras una nueva conversión. | Conservar las previews existentes; construir un ID nuevo cuando exista espacio suficiente y validar los accesos del control plane dentro de la VM. |
| D1-002 | En validación | DrvFS puede devolver `ENODATA` al leer el log serial mientras QEMU sigue escribiendo. El launcher ahora lo trata como transitorio y conserva la VM abierta. | Ejecutar una sesión `--run-existing` con un ID de sesión nuevo y confirmar que la ventana permanece abierta hasta apagarla desde Plasma. |

No se eliminan entradas por apariencia: se cierran con un enlace a evidencia reproducible.
